# agent-sandbox

**Запуск чужого кода с жёсткими лимитами и журналом, который видно, если его правили.**

Агент приносит скрипт «посчитай вот это» — и его надо выполнить, не отдав ему машину целиком. `agent-sandbox` запускает команду под лимитами по времени, процессору, памяти и числу процессов, чистит окружение от секретов и пишет каждый прогон в журнал с цепочкой хешей: однострочную правку истории видно, а вставку или удаление записи — по разрыву цепочки.

Ноль зависимостей, ни Docker-демона, ни root. Лимиты держит ядро: Job Objects на Windows, `rlimit` на POSIX.

## Зачем

Агентские пайплайны и MLOps-обвязка постоянно выполняют сгенерированный код: препроцессинг, бенчмарк, «прогони вот этот скрипт». Обычный `subprocess` в такой ситуации — это доступ к вашим токенам, домашнему каталогу и всей памяти. Полноценный контейнер — правильно, но не всегда есть демон, права и желание ждать сборки образа.

`agent-sandbox` закрывает средний случай:

- **лимиты** — стенное время, процессорное время, память, число одновременно живых процессов;
- **дерево процессов** — умирает целиком, а не оставляет сирот;
- **окружение** — дочерний процесс получает минимум переменных, всё похожее на токен вырезается даже по просьбе политики;
- **журнал** — каждая запись содержит хеш предыдущей, `audit verify` показывает, где цепочка порвалась;
- **коды возврата** — скрипт, оболочка и CI одинаково понимают, что случилось.

## Установка

```bash
python -m pip install -e ".[dev]"
```

Нужен Python 3.11+ и ничего больше. `tomllib` входит в стандартную библиотеку.

## Быстрый старт

```bash
# что умеет эта машина
agent-sandbox doctor

# обычный запуск
agent-sandbox run -- python -c "print('hello from sandbox')"

# лимиты можно переопределить на один прогон
agent-sandbox run --timeout 2 -- python -c "import time; time.sleep(60)"
agent-sandbox run --cpu 2 -- python -c "x=0
while True: x += 1"
agent-sandbox run --memory 64 -- python -c "bytearray(400 * 1024 * 1024)"

# журнал
agent-sandbox audit verify
agent-sandbox audit tail --limit 5
```

Вывод одного прогона:

```
запуск     20261116T220033-93c856
команда    python -c 'import time; time.sleep(60)'
состояние  таймаут  (exit 124)
время      2.02 с, процессор 0.02 с
память     7 МБ
нарушено   стенное время больше 2 с
каталог    runs/20261116T220033-93c856
журнал     audit/audit.jsonl
```

`--json` печатает то же самое машинно-читаемым, `--no-echo` отключает трансляцию вывода задачи в консоль (вывод всё равно остаётся в `runs/<id>/stdout.log`).

## Как это работает

```
команда ──▶ политика (allow / env_keep) ──▶ очистка окружения
                                              │
                                              ▼
                          backend: windows-job | posix-rlimit
                                              │
                                stdout.log / stderr.log / meta.json
                                              │
                                              ▼
                             audit/audit.jsonl (prev → hash)
```

### Windows: Job Objects

Процесс создаётся приостановленным (`CREATE_SUSPENDED`), прицепляется к job-объекту и только потом получает управление через `NtResumeProcess`. Так закрывается гонка на старте: если прицепить процесс после `Popen`, он успевает наплодить детей, которые в job уже не попадут.

Job-объект задаёт:

- `JOB_OBJECT_LIMIT_JOB_TIME` — суммарное процессорное время всей задачи;
- `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` — одновременно живые процессы;
- `JOB_OBJECT_LIMIT_PROCESS_MEMORY` / `JOB_OBJECT_LIMIT_JOB_MEMORY` — предел памяти;
- `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` — при закрытии хендла не остаётся сирот.

Процессорное время и пик памяти читаются из `QueryInformationJobObject`, а не считаются на стороне Python. Свой `PerJobUserTimeLimit` ядро проверяет с задержкой в секунды — для песочницы это слишком много, поэтому сторож опрашивает учёт каждые 50 мс и добивает job сам; лимит ядра остаётся страховкой.

### POSIX: rlimit

`preexec_fn` выставляет `RLIMIT_CPU`, `RLIMIT_AS` и `RLIMIT_CORE` (дампы памяти после падения не нужны), затем `os.setsid()`. Своя сессия нужна, чтобы таймаут убивал всю группу процессов одной командой. Точное время и пик памяти берутся из `os.wait4`.

### Лимиты и коды возврата

| Лимит | Windows | POSIX | Код |
|---|---|---|---|
| стенное время | `TerminateJobObject` по таймауту | `killpg(SIGKILL)` | `124` |
| процессорное время | учёт job + сторож каждые 50 мс | `RLIMIT_CPU` → `SIGXCPU` | `152` |
| память | отказ в выделении на пределе job | `RLIMIT_AS` → `SIGKILL`/`MemoryError` | `137` |
| программа не разрешена | проверка до запуска | проверка до запуска | `126` |
| программа не найдена | `shutil.which` | `shutil.which` | `127` |
| песочница не смогла запустить | `OSError` | `OSError` | `125` |

Коды `124`, `137` и `126/127` совпадают с тем, что печатают `timeout(1)` и оболочка, поэтому проверять результат можно привычным `$?`.

На Windows лимит памяти мягкий по своей природе: ядро не убивает процесс, а отказывает в выделении, и интерпретатор падает сам (`MemoryError`, `bad_alloc`). Такой прогон распознаётся по тексту ошибки в `stderr` и получает состояние `memory-limit`. Лимит числа процессов действует так же мягко: job-объект не даёт создать следующий процесс (`WinError 1816`), а что с этим делать, решает сама задача.

## Политика

Всё, что можно задать до старта чужого кода, лежит в TOML. Скопируйте `sandbox.example.toml` в `sandbox.toml` — сам песочница его не ищет, путь передаётся явно:

```bash
agent-sandbox run --policy sandbox.toml -- python job.py
```

```toml
[limits]
timeout = 30
cpu = 20
memory_mb = 1024
procs = 16

[policy]
allow_programs = ["python", "python3", "node", "bash", "sh", "pwsh", "powershell", "cmd"]
env_keep = ["PATH", "SYSTEMROOT", "TEMP", "TMP", "LANG", "TERM"]

[paths]
audit = "audit/audit.jsonl"
runs = "runs"
```

Заполненный `allow_programs` — это deny-by-default по имени программы. Пустой список означает «разрешено всё»: это осознанный компромисс для локального использования, а не безопасное значение по умолчанию для сервера.

Политика хешируется, отпечаток попадает в каждую запись журнала: по истории видно, под какими правилами шёл прогон.

## Окружение

Дочерний процесс получает только базовые переменные платформы плюс `env_keep`. Дополнительно: `PYTHONNOUSERSITE=1`, `PYTHONUNBUFFERED=1`, `PYTHONDONTWRITEBYTECODE=1`, собственные `TEMP`/`TMP` внутри каталога прогона.

Всё, что похоже на секрет — по имени (`TOKEN`, `SECRET`, `PASSWORD`, `API_KEY`, `CREDENTIAL`, `COOKIE`, `AUTH`, …) или по известному имени (`GH_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `HF_TOKEN`, …), — вырезается. Даже если политика просит оставить такую переменную. Список вырезанного пишется в `meta.json`, но не в консоль.

## Журнал

`audit/audit.jsonl` — по строке на прогон:

```json
{"hash":"…","prev":"…","record":{"id":"…","state":"timeout","exit_code":124,"cpu_s":0.016,"peak_memory_mb":6.7,"command":["python","-c","…"],"stdout":{"sha256":"…"},"policy":{"sha256":"…"}}}
```

`hash` — SHA-256 от канонического JSON записи и `prev`. `agent-sandbox audit verify` проходит цепочку и сообщает номер первой битой строки.

Что это даёт: выборочную правку или удаление строки видно. Что не даёт: защиты от того, кто может переписать файл целиком и пересчитать все хеши. Для этого нужен внешний якорь — отправка хеша в неизменяемое хранилище, отдельный syslog или подпись. Это следующий шаг, а не обещание.

## Чего здесь нет

Честно, потому что иначе этим пользуются неправильно:

- **нет изоляции файловой системы.** Процесс работает под вашим пользователем и читает всё, что читаете вы. `cwd` — это просто рабочий каталог, а не песочница.
- **нет изоляции сети.** Сокеты не ограничены.
- **нет разделения привилегий.** Это не замена контейнеру, `nsjail` или виртуальной машине.
- **лимит числа процессов только на Windows.** На POSIX без cgroups его не сделать средствами `rlimit`; `procs` там принимается, но не действует.
- **лимит памяти на Windows мягкий.** Процесс, который игнорирует ошибки выделения, может продолжать работать; лимит при этом соблюдается, но выглядит это как `MemoryError`, а не как убийство.
- **журнал не защищён от полной перезаписи.** См. выше.

Если нужен настоящий барьер для недоверенного кода — это контейнер с `--network none`, `--read-only` и отдельным пользователем. `agent-sandbox` для другого: удержать случайный или сгенерированный скрипт в рамках и оставить след.

## Разработка

```bash
python -m pip install -e ".[dev]"
ruff check .
pytest -q
```

CI гоняет то же самое на `windows-latest` и `ubuntu-latest`: тесты лимитов платформенные, на чужой ОС они пропускаются, а не притворяются пройденными.

```
agentsandbox/
  backends/windows_job.py   Job Objects: лимиты, приостановленный старт, учёт
  backends/posix_rlimit.py  rlimit, setsid, wait4
  config.py                 Limits, Policy, TOML
  env.py                    очистка окружения
  audit.py                  цепочка хешей, verify, tail
  runner.py                 оркестровка и запись прогона
  report.py                 человеческий вывод
  cli.py                    run | audit | doctor | policy
```
